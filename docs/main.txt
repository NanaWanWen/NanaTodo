================================================================
YonErp 智能采购管理系统 —— 项目描述（完整版）
================================================================

一、项目概述
----------------------------------------------------------------
YonErp 是一套面向企业采购业务的「一体化智能采购管理系统」，目标是打通并模拟
用友 BIP / YonBIP 的采购 P2P（Procure-to-Pay）全链路闭环，并在此基础上落地
一个「数据全部来自系统、AI 只负责语言组织」的对话式智能助手与预警中心。

业务闭环：
  采购申请 → 采购订单 → 两级审批 → 收货入库 → 发票核对 → 付款结算 → 三单匹配
辅助能力：
  报表分析 / 库存预警 / 供应商应付 / 智能预警中心 / AI 对话 Agent

核心设计理念：
  - MySQL 是唯一真源；Redis 只做缓存/会话/锁/防重，不承载业务最终状态。
  - 状态变更只走「动作接口」，禁止用更新接口直接改状态（状态机唯一真源在 DB）。
  - 金额一律 BigDecimal，服务端按明细重算，不信任前端传入金额。
  - AI 回答的「每一个数字」都来自系统实时统计：模型只负责理解意图、组织语言，
    数字与表格由后端工具数据保证，杜绝编造与转述错误。

二、技术栈
----------------------------------------------------------------
后端：Spring Boot 3.x、MyBatis-Plus、MySQL 8、Redis 7
      LangChain4j（通义千问 DashScope / 智谱 GLM，OpenAI 兼容端点）、SSE 流式
安全与治理：拦截器会话、@RequireRole 角色注解 + 切面、PermissionChecker 数据权限
          乐观锁、Redis 幂等/互斥锁、Cache-Aside 缓存、领域事件异步结算
前端：Vite + React 18 + TypeScript + Ant Design 5 + TanStack Query
      React Router 路由守卫、Zustand 用户态、axios 拦截器统一注入身份头
工程：Maven、Docker Compose、统一 Result 响应体、全局异常处理、审计字段注入

三、系统架构
----------------------------------------------------------------
前后端分离：
  React SPA（5173） ──HTTP/JSON(SSE)──> Spring Boot 单体应用（8080）
                                       └──> MySQL 8 / Redis 7

分层（后端）：
  Controller（参数校验→Result） → Service（事务边界/状态机/业务规则）
           → Mapper（MyBatis-Plus + XML 复杂查询） → MySQL
  横切：拦截器（解析 X-User-Id→Redis 会话→CurrentUser）、
        统一响应/全局异常/参数校验/审计填充（MetaObjectHandler）。

简化鉴权：无密码、无 JWT，采用「选择用户 + 切换角色」登录。
  请求头 X-User-Id（必填）+ X-Role-Code（当前角色）。
  后端仍做真实角色与数据权限校验，越权一律 403（前端仅做按钮/菜单显隐）。

四、核心业务域
----------------------------------------------------------------
1) 基础数据域（base）
   用户(sys_user)/角色(sys_role)/用户角色关联、供应商(base_supplier)、
   物料(base_material)、字典(sys_dict)。供应商/物料被引用时不物理删除，仅停用。

2) 采购订单域（po.order）
   - 订单主表 po_order + 明细 po_order_item（数量/单价/税率/含税金额快照）。
   - 状态机：DRAFT → APPROVING → APPROVED / REJECTED / CANCELED。
   - 金额规则：含税金额 = 数量 × 单价 × (1 + 税率/100)，HALF_UP 两位，
     主表 total_qty/total_amount 由服务端按明细重算落库。
   - 收货（po.receipt）：收货确认（CONFIRMED）后扣减库存；超收硬拦截——
     本次实收 + 已确认收货 ≤ 订单行数量，超限抛错并附「缺料清单」
     （如：B 物料还差 200 件，则明确提示应收 B 200 件而非 A）。
     已确认收货单支持取消（冲回库存 + 触发重匹配）。

3) 审批工作流（po.approval）
   - 两级审批：采购经理(node=1) → 总监(node=2)。
   - 任务表 po_approval_task（当前待办）+ 流水表 po_approval_log（全程留痕）。
   - 并发防护：Redis 互斥锁(SET NX) + DB 乐观锁(version) 双保险；
     审批推进在 @Transactional 内，锁在 finally 按 value 校验释放。
   - 支持提交/通过/驳回（意见必填）/撤回/取消，每动作写一条流水。

4) 三单匹配与结算（ap）
   - 用友式改造（三单匹配 2.0）：行级「数量池」多对多勾对
     （一单多收/一票多单/合单开票天然覆盖），差异按 数量→价格→税额→汇差 分类。
   - 多维可配容差：组织/供应商/物料分类/币种 × 比例容差 + 绝对额容差（取大）。
   - 暂估与回冲：货到票未到按订单价月末暂估，票到后单到/月初回冲。
   - 差异处理闭环：超容差自动 HOLD + 预警，工作台提供补收货/退票/调价/放行/
     领导强制匹配（DIRECTOR 审批 + 原因留痕）五个动作。
   - 事件驱动自动结算：收货确认/发票校验提交后(AFTER_COMMIT)发布领域事件，
     @Async + REQUIRES_NEW 异步结算，match_no 唯一索引幂等。
   - 付款联动：付款前校验结算单必须为 MATCHED，差异未解决即拦截。

5) 库存域（po.inventory）
   库存表 po_inventory（现存量/安全库存/占用），收货确认扣减（乐观锁防超卖）。
   低库存预警：现存 ≤ 安全库存 触发。

6) 报表域（po.report）
   订单汇总（总笔数/总金额/各状态分布/已完成统计）、按状态、按时间、
   按维度（供应商/采购员/物料/部门）金额排行 TOP N。统计结果 Redis 缓存 5min，
   订单写操作后失效，保证报表与列表口径一致。

五、智能预警中心（po.alert）
----------------------------------------------------------------
- 策略模式实现 7 类可配置规则：逾期订单、审批超时、价格异常、低库存、超储、
  发票不符、付款逾期。业务角色可自助维护阈值/级别/启停，超阈值 2 倍自动升 CRITICAL。
- 生命周期去重：数据库权威去重优先（handled/ignored 状态唯一），Redis 仅作并发防重
  且 TTL 与扫描间隔联动，避免同一问题被反复复制。
- 规则变更语义：改规则 A 时清除其名下历史预警并按新配置重建，不影响其他规则；
  清除预警同时释放该规则 Redis 去重锁，避免残留锁导致重建不出。
- 推送：SSE 连接集合化（多标签页）+ 30s 心跳保活；前端断线指数退避重连 +
  重连后补偿拉取，彻底防消息丢失。
- 预警处置：卡片「指派/转办」改为真实用户下拉（后端校验对象必须是启用用户），
  操作人留痕；指派/转办后在前端工作台（DiffWorkbench）处理并联动重匹配。

六、AI 对话 Agent（核心子系统）
----------------------------------------------------------------
架构：AgentController(/api/agent/chat  SSE 流式) → AgentServiceImpl（双模式）
      → LangChain4j（通义千问 qwen-max，OpenAI 兼容端点，temperature 0.3）
      → 业务工具 Tools。

运行模式：
  - LLM 模式：配置 DASHSCOPE_API_KEY 时启用，@Tool 注解注册业务工具，
    由大模型按用户提问自主决策工具编排取数。
  - 规则降级模式：无 Key 或 LLM 限流/超时/配额异常时自动降级，
    关键词路由 + 直接调工具，保证 Agent 始终可回答。

业务工具（@Tool）：
  - ReportTool：订单汇总、按状态分布、按时间汇总、按时间状态汇总、
    按维度金额排行 TOP N（含日期区间参数）。
  - OrderTool：订单列表、逾期订单（审批中且期望到货日已过）。
  - InventoryTool：低库存预警、库存列表。
  - SettlementTool：供应商应付余额、三单匹配记录。
  - ReceiptTool：收货单查询。

「数据全部来自系统」的关键保证（本项目最核心的可靠性设计）：
  1. 关键词/语义路由推断时间范围与数据口径：识别「本月/这个月/当月/今天」、
     「我的/我这个/自己」、「咋样/如何/情况」等口语，自动换算日期区间并
     决定是否按当前用户隔离（BUYER 仅本人）。
  2. 后端校正 reconcileWithToolData：
     - 模型自带数据块与系统工具数据不一致 → 整块替换为系统真实数据；
     - 模型未带数据块 → 在末尾追加系统真实数据块。
  3. 确定性结论 buildSummaryText：一旦模型数字被证伪，结论文字也由系统数据
     确定性生成（覆盖 订单汇总 / 状态分布 / 订单&逾期列表 / 低库存 / 库存列表 /
     应付余额 / 金额排行 全部 8 类），不再依赖模型转述。
  4. 空数据固定句式：如「当前没有符合条件的逾期订单/物料/库存记录」，
     避免模型自由发挥输出病句（如早期「订单单」「暂无相关数据单」）。
  5. append 路径也前置系统结论，防止模型叙述数字跑偏。
  6. 提示词约束：默认口径（仅本人）、用词规范（禁用「订单单」等错词）、
     数字必须逐字段照抄、当前基准日期用 {{today}} 模板变量（防编造年份）。
  效果：增删改订单后再次提问，AI 数字实时联动（已 E2E 验证：新增→笔数+1、
        删除→回到原值）；模型即使在「本月完成咋样」这类口语问题上，
        结论也与 MySQL 实时统计逐字段一致。

前端 AgentChat 面板：
  自动解析 SSE 中的 ```json 数据块 → 渲染 Ant Design 表格，note 字段为蓝色提示标签；
  结论文字以「数据来自系统实时统计」前缀明确来源；规则模式下同款渲染。

七、数据一致性与治理要点
----------------------------------------------------------------
- 统一含税金额口径，MoneyUtils 一致；跨表外键引用断裂全部归零。
- 库存扣减乐观锁防超卖；低库存查询列与列比较（修复误将列名当值）。
- 状态、订单、审批任务不进 Redis 实体缓存，直读 DB，杜绝「缓存旧状态误审批」。
- 一键重建脚本（DROP/CREATE + schema + data + 校验），主表金额由明细 UPDATE 回填，
  配一致性校验（头行金额、付款不越界、暂估对收货等）全部归零。
- 审计字段由 MetaObjectHandler 统一注入，操作人来自 CurrentUser，代码不手写。

九、一页简历版（参考目标格式：项目名/项目介绍/技术栈/负责内容）
----------------------------------------------------------------
**YonErp 智能采购管理系统（AI Agent）**

**项目介绍**：面向企业采购场景的一体化智能管理平台：LLM 为底座、Function Calling
工具编排取数、后端数据保真校正，打通"采购订单 → 两级审批 → 收货 → 发票 → 付款 →
三单匹配"的 P2P 完整链路，将"人找数据"转变为"数据找人"，AI 回答的每一个数字
与系统实时数据逐字段一致，单据增删改后对话结果秒级联动。

**技术栈**：Spring Boot 3、MyBatis-Plus、MySQL、Redis、LangChain4j、通义千问
（OpenAI 兼容端点 / Function Calling）、SSE、React、Ant Design 5

**负责内容**：

- **AI 对话 Agent 开发**：基于 LangChain4j AiServices 接入通义千问，注册订单/报表/
  库存/结算/收货 5 类 @Tool，由大模型按用户提问自主决策工具调用编排，取代
  "关键词规则取数 + LLM 润色"模式；系统提示词注入当前日期模板变量防编造年份，
  口语化问法（"这个月/我这个月咋样"）由规则路由换算时间区间与数据口径。

- **数据保真机制（核心）**：针对大模型抄错数字、自由发挥输出病句的问题，设计
  「后端校正 + 确定性结论」双保险——模型数据块与系统实时统计逐字段比对，不一致
  即整块替换为工具真实数据；8 类查询（汇总/状态/列表/低库存/库存/应付/排行）的
  结论文字全部由真实数据确定性生成，空数据固定句式；实测新增/删除单据后 AI
  回答实时联动，数据准确率从"频繁转述出错"提升至 100% 来自系统。

- **多级降级设计**：遍历异常链识别限流/配额/超时（429、Throttling、SocketTimeout）
  判定算力不足，降级时先向对话流推送提示再切换本地关键词路由模式，保证无 Key、
  限流、超时三种场景下 Agent 始终可回答。

- **智能预警中心**：策略模式实现 7 类可配置业务规则（逾期/审批超时/价格异常/
  低库存/超储/发票不符/付款逾期）；修复重复预警 Bug——原 Redis 锁被当放行开关且
  TTL 与扫描间隔错配，导致同一问题每 10 分钟被复制一条（119→1677 条），改为
  数据库权威去重、Redis 仅作并发防重，活跃预警 1677→375；SSE 连接集合化支持
  多标签页 + 30s 心跳保活 + 断线指数退避重连补偿，彻底解决消息丢失。

- **三单匹配用友式改造**：将整单金额比对升级为行级数量池多对多勾对（覆盖一单多收/
  一票多单/合单开票），多维可配容差（组织/供应商/物料分类/币种，比例+绝对额取大）、
  暂估回冲、差异 HOLD 审批闭环（强制匹配需 DIRECTOR 审批留痕）；收货确认/发票
  校验 AFTER_COMMIT 事件驱动异步自动结算，match_no 唯一索引幂等，付款前 MATCHED
  校验拦截。

- **超收硬拦截与数据治理**：收货确认前校验"本次实收 + 已确认收货 ≤ 订单行数量"，
  超限报错并附缺料清单（精确到物料与差量）；已确认收货单取消自动冲回库存并触发
  重匹配；统一全链路含税金额口径，库存乐观锁防超卖，跨表外键引用校验 6 项归零，
  预警转办/指派改为真实用户下拉并后端校验存在性。
